# Анализ влияния — загрузка в СЭД

[Английская версия](impact-analysis.md)

## Изменение бизнес-перспективы

Добавляются правила:

`BR-06` — Загружать можно только локально успешно сформированные PDF.

`BR-07` — Ошибка загрузки не должна отменять или удалять успешный локальный экспорт.

`BR-08` — Пользователь должен различать статус локального экспорта и статус удалённой загрузки.

`BR-09` — Неудачную загрузку можно повторить без повторного экспорта листа, если локальный PDF остаётся корректным.

## Изменение плагина

После локального экспорта плагин получает ответственность за оркестрацию загрузки.

Для каждого элемента:

```text
exportStatus
uploadStatus
remoteDocumentId?
uploadErrorCode?
```

Предлагаемая модель статуса загрузки:

```text
NOT_REQUESTED
PENDING
UPLOADING
UPLOADED
UPLOAD_FAILED
```

Плагин владеет локальной интерпретацией этих статусов.

Он не владеет удалённой истиной, представленной `remoteDocumentId`.

## Изменение файловой системы

Манифест начинает физически хранить локальное состояние загрузки.

Корректный локальный PDF должен оставаться доступным даже при:

```text
отсутствии сети
отказе аутентификации СЭД
тайм-ауте запроса
серверной ошибке СЭД
```

## Новый владелец интеграции

Появляется каноническая область:

```text
integrations/dms/
```

Она должна владеть:

- ответственностью внешней СЭД;
- границей аутентификации;
- контрактом загрузки;
- сопоставлением удалённой идентичности;
- ожиданиями идемпотентности;
- правилами повторных попыток;
- согласованием после неоднозначного тайм-аута;
- специфическими отказами провайдера.

Она **не должна** владеть бизнес-смыслом «успешного экспорта».

## Изменение владения данными

```text
Байты локального PDF
→ Файловая система

Локальный статус экспорта
→ Плагин

Локальный статус попытки загрузки
→ Плагин

Удалённая запись документа
→ СЭД

Связь локального элемента ↔ remoteDocumentId
→ интеграционное отношение, при необходимости сохраняемое локально
```

## Изменение системы

Теперь возможны состояния:

```text
LOCAL_SUCCESS + REMOTE_UPLOADED
LOCAL_SUCCESS + REMOTE_PENDING
LOCAL_SUCCESS + REMOTE_FAILED
LOCAL_FAILED  + REMOTE_NOT_REQUESTED
```

Один общий флаг `SUCCESS/FAILED` больше не способен выразить состояние развившейся системы.

## Изменение структуры

Только теперь архитектура обосновывает:

```text
integrations/
└── dms/
```

Это прямое проявление принципа:

> **Обязательны аналитические перспективы, а не шаблон директорий.**
