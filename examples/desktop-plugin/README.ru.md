# Полный Пример — настольный плагин

[Английская версия](README.md)

> **Статус:** синтетический полный пример  
> **Назначение:** показать связь между рабочим процессом SSAD, стабильным владением знаниями и анализом изменений.

## Сценарий

Вымышленный плагин для настольного приложения CAD экспортирует выбранные листы чертежа в PDF.

Исходное поведение:

- плагин выполняется внутри приложения-хоста CAD;
- пользователь выбирает листы в документе хоста;
- плагин просит приложение-хост экспортировать каждый выбранный лист в PDF;
- сформированные файлы сохраняются в выбранную пользователем локальную папку;
- плагин записывает `export-manifest.json` с результатами экспорта;
- исходный документ не изменяется;
- ошибка одного листа не отменяет успешно экспортированные остальные листы;
- серверная часть, облачная база данных и сетевые зависимости отсутствуют.

Исходная стабильная форма системы:

```text
business/
plugin/
host-application/
filesystem/
system/
```

`backend/`, `frontend/` и `integrations/` не создаются, потому что исходная система не обосновывает таких владельцев.

## Как читать пример

### 1. Разбор процесса

[`walkthrough/`](walkthrough/)

Показывает, **как появляются знания**:

```text
DISCOVER
→ BOUND
→ OWN
→ MODEL
→ CONNECT
→ SYNTHESIZE
→ VERIFY
→ STABILIZE
```

### 2. Базовая версия

[`baseline/`](baseline/)

Показывает, **где находятся получившиеся стабильные знания**:

```text
business/
plugin/
host-application/
filesystem/
system/
```

Ключевое различие SSAD:

> Порядок рабочий процесс не является структурой владения документацией.

### 3. Изменение

[`changes/dms-upload/`](changes/dms-upload/)

Добавляется новый запрос:

> Загружать успешно сформированные PDF во внешнюю систему управления документами.

Изменение создаёт новую внешнюю границу и демонстрирует анализ область влияния изменения.

## Что показывает этот пример

- построение на основе подтверждений даже в синтетическом упражнении;
- определение границы системы до деталей реализации;
- владение раньше контрактов;
- необязательность перспектив;
- стабильную документацию, отражающую систему;
- трассируемость между владельцами;
- поздний системный синтез;
- проверку до статуса Stable;
- появление новой перспективы `integrations/` только тогда, когда реальное изменение её обосновывает.
