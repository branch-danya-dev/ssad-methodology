# Example — настольный плагин

[Английская версия](README.md)

> **Статус:** синтетический пример  
> **Назначение:** показать форму системы, где `backend/` и `frontend/` не являются полезными верхнеуровневыми владельцами.

## Сценарий

Вымышленный плагин для CAD приложения экспортирует выбранные листы чертежа в PDF и сохраняет рядом с результатами манифест экспорта.

Плагин полностью выполняется внутри настольного приложения-хоста.

Допущения:

```text
плагин
CAD-приложение-хост
локальная файловая система
системная служба печати / PDF
нет серверной части
нет облачной базы данных
```

## Возможные перспективы SSAD

```text
business/
plugin/
host-application/
filesystem/
integrations/
system/
```

Именно здесь хорошо виден принцип SSAD: методология не заставляет создавать:

```text
backend/
frontend/
database/
```

если эти перспективы не соответствуют реальной системе.

## Пример владения

```text
оркестрация команды экспорта
→ плагин

открытый документ и выбранные листы
→ приложение-хост

сформированные PDF-файлы
→ файловая система

возможность печати
→ служба ОС

интерпретация результата экспорта
→ плагин
```

## Пример границы

Приложение-хост — не просто «библиотека». Оно владеет состоянием документа и предоставляет среду выполнения, внутри которой работает плагин.

Поэтому для него может быть оправдана отдельная перспектива `host-application/`.

## Пример области влияния изменения

Запрос:

> Автоматически загружать сформированные PDF в систему управления документами.

До изменения:

```text
Плагин → Хост → Файловая система
```

После изменения:

```text
Плагин → Хост
Плагин → Файловая система
Плагин → Внешняя СЭД
```

Граница внешней системы изменяется, поэтому владелец `integrations/` становится существенно важнее.

## Намеренные упрощения

Пример не задаёт конкретного производителя CAD, API плагина, языка программирования, движка PDF или внешней СЭД.
