# Aveli — выводы для методологии

[Английская версия](methodology-findings.md)

## 1. Шаблоны директорий слишком жёсткие

Разным системам требуются разные физические владельцы знаний.

> Обязательны аналитические перспективы, а не одинаковые структуры директорий.

## 2. Владение данными должно предшествовать деталям хранения

```text
владение → концептуальная модель → логическая модель → физическое хранение
```

## 3. Владение технологией следует ответственности

Первоначальная ошибка: Drift и Prisma были сгруппированы вместе с механизмами хранения.

Исправление:

```text
SQLite / PostgreSQL → database
Drift               → frontend
Prisma              → backend
RevenueCat          → integrations
```

## 4. Внутренний API не является внешней интеграцией

```text
Клиент Aveli ↔ сервер Aveli
→ внутренний интерфейс

Aveli ↔ RevenueCat / магазины / ОС
→ внешняя интеграция
```

## 5. Системный уровень лучше работает как поздний синтез

Ранние наброски полезны, но окончательное системное знание должно синтезироваться из достаточно стабильных компонентных подтверждений.

## 6. При переработке старой документации нужно защищать уникальные знания

```text
новый владелец
→ проверка уникальных знаний
→ перенос уникального содержания
→ исправление ссылок
→ удаление дублей
→ проверка согласованности
```

## 7. Stable не означает отсутствие всех будущих вопросов

Стабильная основа может содержать классифицированные будущие решения, требования внешних подтверждений и признаки будущего изменения архитектуры.

## 8. SSAD нужен рабочий процесс, а не только структура

Aveli показала повторяемую схему:

```text
собрать подтверждения → определить границы → определить владельцев → построить модели → связать знания → выполнить системный синтез → проверить → стабилизировать
```

Это расширило SSAD от модели организации документации до модели жизненного цикла системных знаний.
