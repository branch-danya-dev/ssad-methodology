# Integrations

Интеграция — это не просто вызов внешнего API. Это взаимодействие через границу владения, где часть поведения и состояния контролируется другой системой.

## Главный вопрос

> Что происходит, когда наша система зависит от внешнего владельца данных, решения или поведения?

## Почему это отдельная аналитическая перспектива

Внутренний interface связывает две зоны ответственности внутри анализируемой системы. Integration пересекает внешнюю ownership boundary.

Это меняет характер анализа:

- мы не контролируем чужую реализацию;
- внешний контракт может меняться независимо от нас;
- внешняя система может быть недоступна;
- полученные данные могут быть неполными или задержанными;
- внешнее состояние не обязано совпадать с нашим внутренним состоянием;
- нужно явно понимать, кому принадлежит итоговое решение.

## Базовая модель

```text
Our system
   |
   | request / event / evidence
   v
External system
   |
   | response / callback / state
   v
Our system
   |
   v
Internal decision / reconciliation
```

Ключевой вопрос здесь:

> Внешняя система передаёт нам решение или только evidence, на основании которого наша система принимает собственное решение?

## Пример: RevenueCat

RevenueCat может сообщить о состоянии покупки или подписки, но это не означает, что RevenueCat автоматически становится владельцем пользовательского доступа внутри Aveli.

```text
RevenueCat
   |
   | purchase/subscription evidence
   v
Billing
   |
   | reconciliation
   v
Access
   |
   v
Effective user access
```

Такой анализ отделяет:

```text
external evidence
!=
internal authority
```

## Что нужно выяснить

Для каждой интеграции ответьте как минимум на следующие вопросы.

### 1. Где проходит ownership boundary?

Что контролируем мы, а что — внешняя система?

### 2. Что именно приходит извне?

- команда;
- данные;
- событие;
- подтверждение;
- evidence;
- каноническое состояние.

### 3. Кто принимает итоговое решение?

Не путайте источник данных с владельцем решения.

### 4. Как синхронизируется состояние?

```text
request-response?
callback/webhook?
polling?
event stream?
manual reconciliation?
```

### 5. Что происходит при рассинхронизации?

Например:

```text
External: subscription active
Internal: access expired
```

Какая сторона является authority? Как запускается reconciliation?

### 6. Что происходит при недоступности внешней системы?

- fail closed;
- fail open;
- cached state;
- bounded offline trust;
- retry;
- degraded mode;
- manual recovery.

### 7. Какие гарантии даёт внешний контракт?

- идемпотентность;
- порядок событий;
- доставка;
- timeout;
- retry semantics;
- SLA;
- versioning;
- backward compatibility.

## Метод анализа

```text
1. Найдите external ownership boundary.
2. Определите, что именно пересекает границу.
3. Определите владельца итогового решения.
4. Опишите нормальный сценарий.
5. Опишите рассинхронизацию и reconciliation.
6. Опишите недоступность и degraded behavior.
7. Зафиксируйте контракт и его ограничения.
```

## Результат

Хорошо проанализированная интеграция должна позволять объяснить:

```text
что внешняя система знает;
что она может изменить;
что она сообщает нам;
чему мы доверяем;
какое решение принимаем сами;
как восстанавливаем согласованность;
что делаем при сбое.
```

## Типичные ошибки

### Считать интеграцию просто API

HTTP-контракт не объясняет ownership, authority и reconciliation.

### Делать внешний сервис внутренним authority без явного решения

Это создаёт скрытую зависимость бизнес-логики от чужой системы.

### Описывать только happy path

Для внешней границы failure behavior является частью основной модели.

### Не различать stale и authoritative state

Кэш или последний callback могут быть полезны, но не обязательно являются текущей истиной.

## Проверка

Интеграция описана достаточно хорошо, если команда может однозначно ответить:

- кто владеет каждым состоянием;
- что является evidence;
- кто принимает решение;
- как происходит reconciliation;
- что произойдёт при timeout, duplicate, delay и outage.
