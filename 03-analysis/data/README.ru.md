# Data

Данные отвечают на вопрос:

> **Какая информация существует в системе, кто ею владеет, где находится authoritative state и как данные проходят свой жизненный цикл?**

SSAD рассматривает данные не как «таблицы БД», а как часть ответственности системы.

## Порядок анализа

```text
OWNERSHIP
↓
CONCEPTUAL MODEL
↓
LOGICAL MODEL
↓
PHYSICAL STORAGE
↓
CONSTRAINTS / LIFECYCLE / MIGRATIONS
```

Сначала определяется смысл и ownership, а уже затем структура хранения.

## Основные вопросы

```text
Что означает объект данных для системы?
Кто authoritative owner?
Кто может создавать и изменять его?
Кто только читает или кеширует?
Какие поля являются производными?
Какие связи и ограничения существуют?
Как данные создаются, изменяются, архивируются и удаляются?
Как синхронизируются копии?
Что происходит при конфликте или недоступности владельца?
```

## Три уровня

### Conceptual

Какие сущности и понятия существуют независимо от реализации.

### Logical

Какие атрибуты, связи, идентификаторы и ограничения нужны модели.

### Physical

Как это реально хранится: таблицы, коллекции, локальная БД, cache, index и т.д.

## Пример: Aveli

Профессиональный workspace пользователя хранится локально на устройстве, а account/access/billing — на backend.

Это важнее конкретных таблиц, потому что сразу фиксирует две разные зоны ownership:

```text
Device
→ professional workspace

Backend
→ account
→ access
→ billing state
```

Backend не должен становиться владельцем локальных профессиональных данных только потому, что он управляет доступом к приложению.

## Типичные ошибки

- начинать анализ с ERD;
- считать место хранения владельцем знания;
- смешивать canonical state и cache;
- не описывать lifecycle и удаление;
- не определять конфликтующие источники;
- проектировать физическую схему до понимания ответственности.

## Проверка

Для каждого значимого набора данных должно быть понятно:

```text
meaning
owner
writers
readers
constraints
lifecycle
copies
conflict policy
```
