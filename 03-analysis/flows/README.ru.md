# Flows

Flow — это сквозной сценарий, который проходит через несколько зон ответственности, интерфейсов и иногда внешних интеграций.

## Главный вопрос

> Как пользовательское или системное действие проходит через систему от триггера до наблюдаемого результата?

Локальные модели могут быть корректны по отдельности, но система всё равно может быть противоречивой на стыках. Поэтому после локального анализа нужен end-to-end flow.

## Базовая модель

```text
Trigger
  ↓
Zone A
  ↓ interface
Zone B
  ↓ integration
External system
  ↓ callback/evidence
Zone C
  ↓
Observable outcome
```

Flow не заменяет локальные модели. Он проверяет, что они действительно складываются в один сценарий.

## Что нужно отслеживать

Для каждого шага важно видеть:

- кто владеет действием;
- какие данные передаются;
- какой контракт используется;
- какое состояние читается;
- какое состояние изменяется;
- где принимается решение;
- где возможен отказ;
- что наблюдает пользователь или другая система.

## Пример: покупка подписки

```text
User
 ↓
Frontend
 ↓ purchase request
RevenueCat
 ↓ purchase evidence
Backend Billing
 ↓ reconciliation
Access
 ↓ effective access
Frontend
 ↓ refreshed access state
User sees unlocked feature
```

Этот flow позволяет сразу задавать вопросы:

- что если покупка успешна, но callback задержался;
- что если backend недоступен;
- когда frontend имеет право показать доступ;
- что является authority;
- можно ли повторно обработать событие;
- как восстанавливается сценарий после частичного сбоя.

## Метод анализа

```text
1. Определите trigger и ожидаемый observable outcome.
2. Перечислите responsibility zones по порядку.
3. Для каждого перехода укажите interface/integration.
4. Отметьте ownership каждого решения и состояния.
5. Отметьте изменения состояния.
6. Добавьте альтернативные пути.
7. Добавьте failure points.
8. Проверьте сквозные invariants.
```

## Не только happy path

Полезно строить как минимум три варианта:

```text
main flow
alternative flow
failure/recovery flow
```

Например:

```text
Purchase succeeds
→ reconciliation succeeds
→ access activated
```

```text
Purchase succeeds
→ backend temporarily unavailable
→ evidence retained
→ reconciliation later succeeds
→ access activated
```

## Flow и sequence diagram

Sequence diagram — хороший способ визуализировать flow, но diagram является представлением знания, а не самим знанием.

Перед рисованием диаграммы должны быть понятны:

- actors/zones;
- ownership;
- contracts;
- decisions;
- state changes;
- failure behavior.

## Результат

Хороший flow позволяет проследить причинность:

```text
trigger
→ interaction
→ decision
→ state change
→ next interaction
→ observable result
```

и объяснить, что произойдёт при отклонении на любом шаге.

## Типичные ошибки

### Рисовать sequence diagram без ownership

Получается техническая трассировка вызовов, но не системная модель.

### Показывать только сервисы

Flow должен отражать решения, состояния и смысл, а не только HTTP-вызовы.

### Игнорировать альтернативные пути

Happy path редко достаточен для реального системного анализа.

### Дублировать локальные знания

Flow должен связывать локальные модели, а не становиться вторым каноническим владельцем всех контрактов и правил.

## Проверка

Flow достаточно полон, если можно выбрать любой шаг и ответить:

- почему он происходит;
- кто его инициирует;
- какой контракт действует;
- какое состояние используется;
- кто принимает решение;
- что произойдёт при ошибке.
