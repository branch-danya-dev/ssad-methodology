# Failures

Failure analysis отвечает не на вопрос «что может сломаться вообще», а на вопрос:

> **Как система должна вести себя, когда нормальный сценарий больше не выполняется?**

## Почему это часть системного анализа

Если поведение при ошибке не определено, команда всё равно его реализует — только решение окажется случайным и распределённым между frontend, backend, интеграциями и инфраструктурой.

Поэтому failure behavior является такой же частью системного решения, как основной сценарий.

## Базовая модель

```text
Expected interaction
       ↓
Failure condition
       ↓
Detection
       ↓
System decision
       ↓
Fallback / retry / reject / degrade
       ↓
Recovery or stable failed state
```

## Типы failures

Не обязательно создавать универсальную классификацию, но полезно явно искать как минимум следующие группы:

- dependency unavailable;
- timeout;
- invalid input;
- authorization failure;
- stale state;
- conflicting state;
- duplicate request/event;
- partial completion;
- out-of-order event;
- data corruption or missing data;
- local storage failure;
- network loss;
- unsupported version/contract.

## Главные вопросы

Для каждого существенного failure point выясните:

1. Как система узнаёт о проблеме?
2. Кто принимает решение о дальнейших действиях?
3. Какое состояние уже могло измениться?
4. Можно ли безопасно повторить операцию?
5. Нужно ли компенсирующее действие?
6. Что увидит пользователь или внешний consumer?
7. Как система восстановится?
8. Требуется ли ручное вмешательство?

## Пример: частично успешная покупка

```text
RevenueCat confirms purchase
        ↓
Backend reconciliation starts
        ↓
Access update fails
```

Система уже получила внешнее evidence, но итоговое внутреннее состояние не обновилось.

Плохая модель:

```text
show generic error
```

Этого недостаточно, потому что остаются вопросы:

- покупка реально состоялась?
- можно ли повторить reconciliation;
- будет ли повторная обработка идемпотентной;
- что покажет frontend;
- как система позже восстановит доступ;
- нужно ли хранить pending state.

Более системная модель:

```text
Purchase evidence received
        ↓
Reconciliation pending
        ↓
Retry / recovery process
        ↓
Access activated
```

или явный terminal failure с ручным восстановлением, если автоматическое восстановление невозможно.

## Partial failure

Для распределённых сценариев особенно важно анализировать промежуточные состояния.

```text
A succeeded
B succeeded
C failed
```

Вопрос не только в том, почему C упал.

Нужно понять:

```text
что теперь означает состояние всей операции?
что уже нельзя откатить?
что можно повторить?
что должен знать следующий участник?
```

## Retry semantics

Retry — это не универсальное решение.

Перед retry нужно понимать:

- операция идемпотентна или нет;
- может ли первый запрос всё-таки завершиться позже;
- как определяется duplicate;
- есть ли request/event identifier;
- когда retry прекращается;
- что происходит после исчерпания попыток.

## Fail open / fail closed

Для решений доступа, безопасности и критичных ограничений нужно явно определить поведение при недоступности authority.

```text
fail closed
→ запрещаем действие без подтверждения

fail open
→ временно разрешаем действие без подтверждения

bounded trust
→ используем ранее подтверждённое состояние только в заданном окне
```

Это должно быть осознанным системным решением.

## Метод анализа

```text
1. Возьмите основной flow.
2. Найдите meaningful failure points.
3. Для каждого определите detection.
4. Проверьте уже совершённые state changes.
5. Определите retry/compensation/degraded behavior.
6. Определите observable result.
7. Определите recovery path.
8. Проверьте system invariants после failure.
```

## Результат

Хорошая failure-модель позволяет ответить:

```text
что сломалось;
как мы это поняли;
какое состояние осталось;
что система делает дальше;
что видит consumer;
как восстанавливается согласованность.
```

## Типичные ошибки

### «Вернём 500»

HTTP status — это сигнал интерфейса, а не описание системного поведения.

### Retry без идемпотентности

Может привести к повторной покупке, двойной записи или повторному side effect.

### Ошибка без состояния

Если не понятно, что уже изменилось до сбоя, recovery невозможно спроектировать корректно.

### Скрытый manual recovery

Если автоматическое восстановление невозможно, ручной путь должен быть явной частью operational behavior.

## Проверка

Failure analysis достаточен, если для основных сбоев команда знает:

- detection;
- authority решения;
- resulting state;
- retry/compensation rules;
- observable behavior;
- recovery path;
- invariants, которые должны сохраниться.

После анализа failures возвращайтесь к [`../synthesis/`](../synthesis/) и проверяйте систему целиком.
