# Участие в развитии SSAD

[English version](CONTRIBUTING.md)

Спасибо за интерес к развитию SSAD.

SSAD — это методология системного анализа, а не каталог шаблонов документов. Изменения должны делать подход понятнее, проверяемее и практичнее, не превращая его в жёсткий универсальный стандарт.

## Перед изменением

Сначала определите тип вклада:

- **clarification** — улучшение формулировки без изменения смысла;
- **method improvement** — улучшение способа решения аналитической задачи;
- **practice improvement** — новый или улучшенный task-based checklist;
- **example** — демонстрация существующего принципа SSAD на конкретной системе;
- **consistency fix** — терминология, навигация или выравнивание RU/EN;
- **methodology change** — изменение принципа, responsibility boundary или модели рассуждения.

Последний тип требует особенно внимательной проверки, потому что может затронуть несколько разделов.

## Принципы contribution

### 1. Меняйте владельца знания, а не каждое упоминание

Если меняется каноническое правило, сначала обновляется его canonical owner. Соседние главы обычно должны обновить только контекст или ссылки.

> Не создавайте вторую истину только ради локальной самодостаточности документа.

### 2. Начинайте с системного вопроса, а не с типа артефакта

Предложение должно отвечать:

```text
Какую системную проблему это решает?
Какая responsibility владеет знанием?
Как аналитик применяет метод?
Как проверить результат?
```

Не стоит добавлять новый top-level раздел только потому, что такой тип документа существует в другой методологии.

### 3. Сохраняйте progressive depth

Root README и overview-файлы должны оставаться компактными. Детальное рассуждение принадлежит главе-владельцу.

Читатель должен двигаться так:

```text
overview
→ выбрать вопрос
→ открыть нужную главу
→ углубляться по ссылкам только при необходимости
```

### 4. Evidence раньше абстракции

Новый концепт желательно подтверждать хотя бы одним из источников:

- повторяющаяся реальная аналитическая проблема;
- конкретный проектный кейс;
- противоречие или ограничение текущей модели;
- evidence из implementation / QA / operations;
- явное снижение неоднозначности или стоимости анализа.

Не добавляйте абстракцию только ради полноты классификации.

### 5. RU и EN должны быть семантически равны

Буквальный построчный перевод не требуется, но обе версии должны передавать одну методологию:

- одинаковую ответственность главы;
- одинаковый reasoning method;
- одинаковые важные примеры;
- одинаковые completion criteria;
- одинаковую навигационную роль.

## Checklist перед Pull Request

- [ ] У изменения есть понятная аналитическая цель.
- [ ] Понятен canonical owner изменяемого знания.
- [ ] Не создана конкурирующая дублированная истина.
- [ ] Соседние знания связываются ссылками, а не копируются без необходимости.
- [ ] RU и EN сохраняют семантическую эквивалентность.
- [ ] Примеры остаются примерами, а не вторым владельцем project truth.
- [ ] Сохраняется progressive depth.
- [ ] Не вводится универсальный folder/template requirement без сильного обоснования.
- [ ] Результат можно объяснить через реальную работу системного аналитика.

## Что обычно не должно становиться содержимым SSAD

SSAD не должен полностью переписывать внешние стандарты и инструменты.

Например, репозиторий не должен превращаться в отдельный учебник по:

- UML;
- BPMN;
- C4;
- OpenAPI;
- SQL;
- ADR;
- Jira / backlog practices;
- architecture frameworks.

SSAD может объяснить, **когда и зачем** инструмент помогает ответить на системный вопрос, а затем дать небольшой пример или ссылку наружу.

## Examples и case studies

Пример должен отвечать:

```text
Какой принцип SSAD демонстрируется?
Какой реальный системный вопрос разбирается?
Как выглядел ход рассуждения?
Где живёт canonical project knowledge?
```

Истина реального проекта по возможности должна оставаться в проектном репозитории.

## Methodology changes

Предложение, меняющее саму методологию, должно объяснять:

1. ограничение текущего подхода;
2. evidence существования проблемы;
3. предлагаемое изменение;
4. затронутые главы и понятия;
5. что становится проще или корректнее;
6. возможные регрессии и новые неоднозначности;
7. как проверить изменение на реальном кейсе.

Для простой редакционной правки такой формальности не требуется.

## Как смотреть на review

Хороший review SSAD спрашивает не только «хорошо ли написан текст?».

```text
Корректен ли системный смысл?
Ясен ли ownership?
Помогает ли метод аналитику действовать?
Не дублирует ли он существующее знание?
Сохраняет ли форму методологии?
Выдерживает ли идея реальный пример?
```
