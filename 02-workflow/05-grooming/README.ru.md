# 05 · Grooming

[English version](README.md)

Grooming — этап, на котором проверяется не столько корректность системного решения, сколько **общее понимание delivery-командой предстоящей реализации**.

Главный вопрос:

> Одинаково ли аналитик, разработчики, QA и другие участники понимают scope, поведение, зависимости и критерии готовности задачи?

## Review и Grooming — не одно и то же

```text
REVIEW
→ правильно ли спроектировано решение?

GROOMING
→ одинаково ли команда понимает, что и как нужно реализовать?
```

На Review может участвовать ограниченный набор владельцев знаний.

На Grooming решение уже рассматривается как будущая работа команды.

## Что обсуждается

Grooming должен дать ответы как минимум на следующие вопросы:

- какая проблема решается;
- что входит в scope;
- что явно не входит;
- какие компоненты затронуты;
- какие зависимости существуют;
- какие контракты изменяются;
- какие edge cases важны;
- есть ли миграции или compatibility concerns;
- как QA сможет проверить результат;
- есть ли блокирующие неизвестные;
- можно ли разбить работу на независимые задачи.

## Метод

### 1. Начать с системного контекста

Команда должна сначала понять изменение целиком.

```text
Problem
↓
Change Surface
↓
Affected components
↓
Expected behavior
```

Только затем имеет смысл обсуждать отдельные implementation tasks.

### 2. Пройти сквозной сценарий

Для значимого изменения полезно буквально пройти путь данных или поведения:

```text
User action
→ Frontend
→ API
→ Backend rule
→ Storage / integration
→ Response
→ Frontend state
→ User-visible result
```

Это быстро выявляет разное понимание границ между участниками.

### 3. Проверить зависимости между задачами

Например:

```text
Backend contract
      ↓
Frontend implementation
      ↓
QA end-to-end scenario
```

Если frontend нельзя начать до стабилизации backend contract, это должно быть явно видно.

### 4. Проверить Ready state

SSAD не требует универсального Definition of Ready, но предлагает минимальный смысловой check:

```text
Purpose understood
Scope defined
Affected owners known
Behavior understood
Contracts sufficiently stable
Dependencies known
Acceptance criteria testable
Critical OPEN questions absent
```

### 5. Новые вопросы возвращать в знание

Grooming не является последней возможностью уточнить задачу.

Если разработчик спрашивает:

> Что происходит, если пользователь меняет аккаунт офлайн?

и ответа нет, это не просто «вопрос на встрече».

Это обнаруженный пробел в модели, который должен быть возвращён в Analysis / Specification.

## Пример · Aveli

Изменение: ограниченный offline access.

На Grooming команда проходит сценарий:

```text
Backend verifies access
        ↓
returns AccessStatus + recheckAt
        ↓
Frontend stores trusted snapshot
        ↓
network unavailable
        ↓
Frontend checks snapshot validity
        ↓
workspace opens or remains blocked
```

QA задаёт вопрос:

> Что произойдёт, если `recheckAt` отсутствует?

Если ранее это не было явно описано, команда возвращает вопрос в системное знание и фиксирует fallback rule.

## Что должно получиться

К концу Grooming команда должна иметь согласованное представление:

```text
What
Why
Where
Dependencies
Expected behavior
Edge cases
Acceptance
Implementation split
```

Это не означает, что каждая техническая деталь уже известна.

Это означает, что **неизвестность не скрыта и не мешает начать реализацию согласованного scope**.

## Типичные ошибки

- сразу обсуждать story points, не поняв изменение;
- читать спецификацию вслух вместо прохождения системного сценария;
- оставлять вопросы только в устном обсуждении;
- считать, что разработчик сам уточнит неоднозначность во время реализации;
- смешивать новый feature request с текущим scope;
- декомпозировать задачи раньше, чем понятны зависимости.

## Completion check

- [ ] команда понимает цель;
- [ ] scope / out of scope известны;
- [ ] основные сценарии пройдены;
- [ ] зависимости между компонентами и задачами понятны;
- [ ] контракты достаточно стабильны для начала работы;
- [ ] QA понимает, как проверять результат;
- [ ] критические вопросы не спрятаны;
- [ ] новые факты и решения возвращены в SSAD-знание;
- [ ] реализацию можно осмысленно декомпозировать.
