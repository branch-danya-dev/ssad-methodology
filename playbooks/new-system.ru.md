# Практический сценарий — новая система

[Английская версия](new-system.md)

## Когда применять

Использовать для нового продукта, сервиса, плагина, платформы или крупной подсистемы, когда нет достоверной существующей основы, которую требуется восстанавливать.

## Главная цель

Создать **минимальную достоверную аналитическую основу**, на которую можно безопасно опирать последующее проектирование.

Цель не в том, чтобы выпустить все возможные документы.

## Исходные данные

Полезными источниками могут быть:

```text
бизнес-проблема
цели заинтересованных сторон
идея продукта
известные пользователи и участники
ограничения
внешние платформы
регуляторные требования
организационные стандарты
первоначальные технические предположения
```

Неизвестные допустимы. Скрытые неизвестные — нет.

## Шаг 1 — DISCOVER: собрать подтверждения

Зафиксировать то, что действительно известно.

Значимые утверждения классифицировать:

```text
VERIFIED
INFERRED
OPEN
```

Предпочитаемую архитектуру нельзя выдавать за подтверждённый факт.

### Результат

- реестр подтверждений;
- начальный словарь;
- реестр открытых вопросов;
- известные ограничения.

## Шаг 2 — BOUND: определить анализируемую систему

Нужно явно ответить:

```text
какую проблему решает система
кто с ней взаимодействует
что входит в область
что находится вне области
какие внешние системы существуют
какая авторитетность остаётся снаружи
```

Не начинать с директорий.

### Контрольная точка

Читатель должен уметь объяснить, где система начинается и заканчивается.

Если нет — остаёмся на этом этапе.

## Шаг 3 — OWN: определить ответственность и владение состоянием

Для каждой значимой ответственности или состояния спросить:

```text
Кто принимает решение?
Кто хранит каноническое состояние?
Кто может его изменять?
Кто использует?
Кто проверяет корректность?
```

Особенно искать конкурирующие источники истины.

### Контрольная точка

У значимого состояния не должно быть двух случайных канонических владельцев.

## Шаг 4 — вывести аналитические перспективы

Только теперь определяются физические владельцы знаний.

Например:

```text
business/
plugin/
host-application/
filesystem/
system/
```

или:

```text
business/
services/
messaging/
data/
operations/
system/
```

Перспектива создаётся потому, что она нужна системе, а не потому, что существует в другом репозитории SSAD.

## Шаг 5 — MODEL: детализировать по зависимостям

Детализировать только то, что уже обосновано стабилизированными исходными знаниями.

Типичный порядок:

```text
бизнес-правила / требования
→ владение данными / жизненный цикл
→ ответственности
→ интерфейсы / интеграции
→ состояния / отказы
→ технологии и использование
```

Это не обязательный перечень артефактов.

То, чего в системе нет, не моделируется.

## Шаг 6 — CONNECT: связать знания

Построить граф поверх иерархии.

Связывать:

```text
бизнес-правило ↔ требование
требование ↔ компонент
владелец ↔ потребитель
производитель ↔ интерфейс ↔ потребитель
технология ↔ место использования
владелец данных ↔ хранение / потребитель
требование ↔ приёмка
```

Канонические определения нельзя дублировать только ради удобства навигации.

## Шаг 7 — SYNTHESIZE: выполнить системный синтез

Знания уровня всей системы формируются после достаточного понимания локальных владельцев.

Обычно сюда входят:

```text
контекст системы
отношения компонентов
сквозные сценарии
карта доверия / авторитетности
движение данных между компонентами
системные инварианты
сквозные сценарии отказов
```

## Шаг 8 — VERIFY: проверить

Как минимум проверить:

```text
бизнес ↔ техническое поведение
владение ↔ контракты
логические данные ↔ хранение
производитель ↔ потребитель
диаграмма ↔ текст
требование ↔ приёмка
системный синтез ↔ локальные владельцы
```

Противоречие возвращает анализ к исходному знанию.

Нельзя исправлять проблему только в системном резюме.

## Шаг 9 — STABILIZE: стабилизировать

Зрелость повышается осознанно:

```text
Draft
→ Baseline
→ Stable
```

Статус `Stable` означает, что знание достаточно надёжно для использования как исходная зависимость.

Это не означает завершённую реализацию.

## Ожидаемые результаты

После успешного прохода обычно остаются:

- явные область и граница;
- явное владение;
- перспективы, отражающие систему;
- достаточное описание поведения, данных и интерфейсов;
- трассируемость;
- открытые вопросы;
- системный синтез;
- классификация зрелости.

## Когда возвращаться назад

Возврат нужен, если:

- новый участник меняет область;
- у ответственности нет понятного владельца;
- два компонента претендуют на одно каноническое состояние;
- контракт требует поведения, которого нет в бизнес-правилах;
- ограничение реализации ломает исходное предположение;
- проверка обнаруживает противоречие.

## Типичные ошибки

### Начинать с шаблона директорий
Результат: искусственные владельцы и пустые области.

### Проектировать API до владения
Результат: контракт закрепляет случайное распределение ответственности.

### Выбирать технологии до границ
Результат: архитектура начинает объясняться инструментами, а не задачей системы.

### Считать любой неизвестный вопрос блокером
Результат: анализ не движется.

### Игнорировать неизвестные
Результат: предположения незаметно превращаются в архитектурные решения.

## Условия завершения

Основа готова к использованию, когда:

```text
область понятна
основные владельцы явны
значимое поведение трассируется
системный синтез согласован с локальными знаниями
существенные противоречия закрыты
оставшаяся неопределённость обозначена явно
```
