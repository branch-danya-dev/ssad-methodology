# Практический сценарий — изменение

[Английская версия](change.md)

## Когда применять

Использовать, когда уже существует достоверная модель системы со зрелостью `Baseline` или `Stable` и приходит значимое изменение.

Например:

```text
новая функция
изменение бизнес-правила
новая интеграция
смена провайдера
замена технологии
изменение схемы
требование безопасности
регуляторное требование
архитектурное изменение
миграция данных
```

## Главная цель

Понять **реальную область влияния изменения** до переработки зависимых деталей.

Значимое изменение не должно начинаться с вопросов:

```text
Какой файл изменить?
Какую конечную точку API добавить?
Какую технологию установить?
```

Первый вопрос:

> **Каких владельцев системного знания затрагивает изменение?**

## Исходные данные

Минимально полезны:

```text
запрос на изменение
причина / желаемый результат
текущий baseline
известные ограничения
затронутый смысл для заинтересованных сторон
новые внешние обязательства, если есть
```

Запрос может содержать предлагаемое решение, но его нельзя автоматически считать настоящей потребностью системы.

## Шаг 1 — нормализовать запрос

Отделить желаемый результат от преждевременной реализации.

Плохо:

```text
Добавить Redis.
```

Лучше:

```text
Снизить повторные вычисления состояния доступа при ожидаемой нагрузке.
```

Плохо:

```text
После экспорта вызвать API СЭД.
```

Лучше:

```text
Позволить сохранять успешно экспортированные документы во внешней СЭД.
```

## Шаг 2 — построить область влияния

Первичный проход:

| Вопрос | Результат |
|---|---|
| Бизнес-поведение | ДА / НЕТ / НЕИЗВЕСТНО |
| Граница системы | ДА / НЕТ / НЕИЗВЕСТНО |
| Владение | ДА / НЕТ / НЕИЗВЕСТНО |
| Данные | ДА / НЕТ / НЕИЗВЕСТНО |
| Компоненты | ДА / НЕТ / НЕИЗВЕСТНО |
| Внутренние интерфейсы | ДА / НЕТ / НЕИЗВЕСТНО |
| Внешние интеграции | ДА / НЕТ / НЕИЗВЕСТНО |
| Технологии | ДА / НЕТ / НЕИЗВЕСТНО |
| Доверие / безопасность | ДА / НЕТ / НЕИЗВЕСТНО |
| Отказы / восстановление | ДА / НЕТ / НЕИЗВЕСТНО |
| Приёмка | ДА / НЕТ / НЕИЗВЕСТНО |
| Трассируемость | ДА / НЕТ / НЕИЗВЕСТНО |
| Эксплуатация | ДА / НЕТ / НЕИЗВЕСТНО |

`НЕИЗВЕСТНО` — полезный результат. Он означает, что вопрос нужно исследовать до детализации.

## Шаг 3 — проверить границу раньше локального дизайна

Спросить:

```text
Появляется новый внешний участник или система?
Данные иначе пересекают границу?
Ответственность перемещается внутрь или наружу?
Ранее внутреннее взаимодействие становится внешним?
В решение входит новый внешний авторитетный источник?
```

При ответе ДА пересматривается контекст системы и затронутые перспективы.

## Шаг 4 — проверить владение

Спросить:

```text
Перемещается каноническое состояние?
Появляется новый источник истины?
Потребитель становится владельцем?
Кэш становится авторитетным?
Внешний провайдер начинает владеть частью истины?
```

Контракт нельзя проектировать раньше понимания авторитетности.

## Шаг 5 — проверить данные и жизненный цикл

Для затронутых данных определить:

```text
владельца
создание
право изменения
потребителей
хранение
синхронизацию
миграцию
срок хранения
удаление
конфиденциальность
согласование состояний
```

Даже замена технологии может влиять на жизненный цикл данных.

## Шаг 6 — проверить интерфейсы и интеграции

Для каждого изменённого пересечения определить:

```text
производителя
потребителя
семантический контракт
транспорт
аутентификацию
авторизацию
совместимость
идемпотентность
повторы
тайм-ауты
согласование
владение отказом
```

Внутренние интерфейсы и внешние интеграции остаются разными объектами анализа.

## Шаг 7 — проверить компоненты и технологии

Только теперь рассматривается изменение реализации.

Технология анализируется **после ответственности**.

При замене технологии спросить:

```text
Какую ответственность она реализует?
Где используется?
Кто от неё зависит?
Какое ограничение вызвало замену?
Меняется владение?
Меняется поведение времени выполнения?
Меняются отказы?
```

## Шаг 8 — проверить доверие, отказы и восстановление

Для каждого нового сценария отказа:

```text
Что может сломаться?
Возможен частичный успех?
Кто авторитетен при расхождении?
Какое состояние переживает отказ?
Можно повторить операцию?
Безопасен ли повтор?
Как согласуется неоднозначный результат?
Что нельзя удалять или делать недействительным?
```

## Шаг 9 — обновить приёмку до завершения дизайна

Определить наблюдаемый успех и отказ.

Например:

```text
Пользователь различает локальный успех и удалённую ошибку.
Миграция сохраняет все записи, удовлетворяющие инварианту X.
Ошибка нового провайдера не отменяет корректное локальное состояние.
Старые и новые клиенты совместимы во время перехода.
```

Изменение без наблюдаемой приёмки смоделировано не полностью.

## Шаг 10 — обновлять канонических владельцев по зависимостям

Не редактировать все затронутые документы одновременно.

Предпочтительный порядок:

```text
бизнес / решение
→ граница / владение
→ данные
→ интерфейсы / интеграции
→ компоненты
→ технологии
→ системный синтез
→ приёмка / трассируемость
```

Меняются только реально затронутые знания.

## Шаг 11 — VERIFY: проверить изменение

Проверить:

```text
новое знание ↔ новое знание
```

и:

```text
новое знание ↔ неизменённый baseline
```

Изменение может быть внутренне непротиворечивым и одновременно ломать старый инвариант.

Проверить:

```text
старые инварианты
совместимость
сохранность данных
авторитетность
поведение при отказе
перекрёстные ссылки
диаграммы
приёмку
```

## Шаг 12 — повторно стабилизировать

Затронутое знание временно может пройти:

```text
Stable
→ Draft / Baseline
→ Stable
```

Незатронутое знание сохраняет статус `Stable`.

Не нужно делать весь репозиторий нестабильным из-за одной функции.

## Ожидаемые результаты

После значимого изменения должны остаться:

- нормализованное описание изменения;
- область влияния;
- список затронутых владельцев;
- обновлённая граница или владение, если требуется;
- изменения данных, интерфейсов и компонентов;
- новые или изменённые инварианты;
- обновлённая приёмка;
- трассируемость;
- результат проверки;
- новая зрелость затронутых знаний.

## Ветка: изменение интеграции

Дополнительно усилить анализ:

```text
внешней авторитетности
аутентификации
контракта провайдера
идемпотентности
повторов
тайм-аутов
согласования
специфических отказов провайдера
```

Полный пример: [`../examples/desktop-plugin/changes/dms-upload/`](../examples/desktop-plugin/changes/dms-upload/)

## Ветка: архитектурное изменение

Если ответственность перемещается между крупными компонентами:

```text
повторно открыть BOUND
→ повторно открыть OWN
→ перестроить затронутые зависимые знания
```

Архитектурное изменение нельзя представлять как набор локальных правок.

## Ветка: замена технологии

Если ответственность не меняется:

```text
владение может остаться стабильным
```

но всё равно проверяются:

```text
поведение времени выполнения
отказы
эксплуатация
миграция
совместимость
ограничения производительности и ёмкости
```

## Ветка: миграция данных

Дополнительно проверить:

```text
исходную авторитетность
целевую авторитетность
переключение
стратегию двойной записи / чтения
откат
сопоставление идентичности
защиту от потерь
совместимость
проверку после миграции
```

## Типичные ошибки

### Начинать с предлагаемого решения
Запрос может содержать проектное предположение, а не реальную потребность.

### Менять только самый очевидный компонент
Одна функция может затрагивать бизнес, данные, доверие, интеграции и приёмку.

### Ставить НЕТ без проверки
Если перспектива не проверена, правильный ответ — `НЕИЗВЕСТНО`.

### Забывать старые инварианты
Новое поведение должно сосуществовать с сохраняющими силу гарантиями базовой версии.

### Создавать новую перспективу заранее
Новая директория появляется только тогда, когда изменившаяся система создаёт нового канонического владельца.

## Условия завершения

Затронутые знания могут вернуться в статус `Stable`, когда:

```text
область влияния разрешена
затронутое владение явно
новые контракты соответствуют авторитетности
жизненный цикл данных согласован
новые отказы имеют модель восстановления
старые действующие инварианты сохранены или осознанно изменены
приёмка наблюдаема
трассируемость объясняет причину каждого значимого изменения
```
