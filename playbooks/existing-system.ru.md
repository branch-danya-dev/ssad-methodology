# Практический сценарий — существующая система

[Английская версия](existing-system.md)

## Когда применять

Использовать, когда система уже существует, но аналитическая основа отсутствует, устарела, разрознена, противоречива или слишком повторяет структуру реализации.

Типичные ситуации:

```text
устаревшая система
недокументированный сервис
миграция документации
восстановление архитектуры
передача системы
аудит
анализ перед рефакторингом
анализ перед миграцией
```

## Главная цель

Восстановить **достоверную модель текущего состояния** до начала проектирования целевого.

Первая задача — не улучшить архитектуру.

Первая задача — понять архитектуру, которая реально существует.

## Исходные данные

Предпочтительны прямые подтверждения:

```text
исходный код
конфигурация времени выполнения
контракты API
схемы баз данных
манифесты развёртывания
контракты провайдеров
тесты
журналы событий
наблюдаемое поведение
существующая документация
знания заинтересованных сторон
история инцидентов
```

Существующая документация является подтверждением, но не автоматической истиной.

## Шаг 1 — DISCOVER: построить карту подтверждений

Собрать подтверждения и оценить их надёжность и применимость.

Для значимых утверждений использовать:

```text
VERIFIED
INFERRED
OPEN
```

Противоречия фиксировать явно.

Пример:

```text
Старый документ:
«Service A владеет статусом клиента»

База:
customer_status хранится в Service B

Выполнение:
Service A читает статус из Service B

→ утверждение о владении OPEN / вероятно устарело
```

## Шаг 2 — разделить текущее и целевое состояние

Установить жёсткое различие:

```text
CURRENT
≠
TARGET
```

Нельзя незаметно переписывать текущее поведение под желаемую архитектуру.

Улучшение оформляется как предложение или целевое состояние.

## Шаг 3 — BOUND: восстановить реальную границу

Определить:

```text
реальных участников
реальные внешние системы
реальные компоненты времени выполнения
реальные пересечения данных
реальные границы авторитетности
реальные эксплуатационные зависимости
```

Фактически используемая зависимость входит в текущее состояние, даже если раньше её никто не документировал.

## Шаг 4 — OWN: восстановить каноническую ответственность

Для каждого значимого состояния или решения спросить:

```text
Кто реально его записывает?
Кто может его изменять?
К кому обращаются при расхождении?
Где находится авторитетное хранение?
Кто только кэширует или зеркалирует состояние?
```

Реализация может показать владение, скрытое старой диаграммой.

## Шаг 5 — вывести перспективы из существующей системы

Не сохранять старые директории только потому, что они уже есть.

Но и не удалять их сразу.

Сначала определить новых канонических владельцев.

Например:

```text
business/
services/
data/
messaging/
integrations/
operations/
system/
```

## Шаг 6 — безопасно мигрировать старые знания

Перед удалением или перестройкой документации:

```text
1. определить нового канонического владельца
2. проверить старые файлы на уникальные знания
3. перенести уникальное содержание
4. исправить ссылки
5. удалить дубли и устаревшие определения
6. повторить проверку согласованности
```

Нельзя удалять устаревший файл до проверки его уникального содержания.

## Шаг 7 — MODEL: описать текущее поведение

Приоритет:

```text
реальное бизнес- и системное поведение
реальное владение данными
реальные интерфейсы
реальные отказы
реальные границы доверия и безопасности
реальное использование технологий
```

Если реализация расходится с намерением, фиксировать оба состояния:

```text
CURRENT
→ что существует

INTENDED / TARGET
→ что должно измениться
```

## Шаг 8 — CONNECT: связать знания с подтверждениями

Значимые утверждения по возможности должны иметь опору.

Например:

```text
владение API
→ OpenAPI + код производителя

владение данными
→ схема + путь записи

поведение провайдера
→ контракт провайдера

зависимость времени выполнения
→ развёртывание / конфигурация
```

Так вывод не превращается незаметно в факт.

## Шаг 9 — SYNTHESIZE: собрать текущее системное представление

После согласования локальных владельцев построить:

```text
контекст текущей системы
компонентную модель
сквозные сценарии
карту доверия / авторитетности
движение данных между компонентами
системные инварианты
текущую модель отказов
```

Системный уровень синтезирует и не заменяет канонических владельцев.

## Шаг 10 — VERIFY: проверить

Особенно проверить:

```text
документация ↔ реализация
диаграмма ↔ топология времени выполнения
производитель API ↔ потребитель
схема ↔ модель данных
заявленный владелец ↔ реальный путь записи
current ↔ target
```

Противоречие либо разрешается, либо остаётся явно `OPEN`.

## Шаг 11 — STABILIZE: стабилизировать

Повышать зрелость только достаточно подтверждённого знания.

Типичный результат:

```text
Stable
→ границы и владение высокой уверенности

Baseline
→ достаточно подтверждённое поведение и модели

Draft
→ детали реализации, которые ещё исследуются
```

## Ожидаемые результаты

- реестр подтверждений;
- граница текущего состояния;
- карта канонического владения;
- явное разделение текущего и целевого состояния;
- мигрированная документация по структуре системы;
- трассируемость к реализации;
- системный синтез;
- реестр открытых вопросов;
- зрелость знаний.

## Ветка: миграция старой документации

Если задача звучит как «перенести документацию в SSAD», **не начинать с перемещения файлов**.

Сначала восстановить владение.

Миграция — следствие понимания, а не упражнение по файловому менеджменту.

## Ветка: рефакторинг

Если планируется рефакторинг:

```text
Existing System
→ Stable current baseline
→ Change
→ целевой рефакторинг
```

Текущее состояние и целевая архитектура не должны сливаться в один проход.

## Типичные ошибки

### Доверять документации больше, чем наблюдаемому поведению системы
Старый документ может описывать намерение, а не реальность.

### Доверять коду без контекста
В коде могут быть мёртвые ветки, совместимость и временные обходы.

### Считать каждую таблицу владельцем домена
Физическое хранение не всегда равно семантическому владению.

### «Исправлять» противоречия
Противоречие — это информация. Его нужно сохранить до решения.

### Мигрировать папки раньше знаний
Так старая неоднозначность просто переносится в новое дерево.

## Условия завершения

Система готова стать базовой версией, когда:

```text
текущая граница явна
основные владельцы подтверждены
current и target разделены
уникальные старые знания сохранены
системные представления согласованы с компонентными подтверждениями
существенные противоречия закрыты или обозначены OPEN
```

После этого для целевых изменений используется [`change.ru.md`](change.ru.md).
