# Initial Scope

Изменение существующей системы начинается не с решения и не со списка файлов, которые нужно обновить.

Оно начинается с ответа на вопрос:

> **Что именно пользователь, бизнес или команда хочет изменить в наблюдаемом поведении системы?**

## Проблема

Формулировка задачи почти всегда уже содержит предполагаемое решение:

```text
Добавить поле в API.
Перенести проверку на backend.
Сохранять статус в БД.
Добавить webhook.
```

Если принять такую формулировку как scope, аналитик рискует анализировать только предложенный технический способ и не увидеть реальную поверхность изменения.

## Идея

Initial Scope — это минимальная исходная граница изменения, сформулированная через ожидаемый эффект, затронутый сценарий и известные ограничения.

```text
REQUEST
  ↓
EXPECTED CHANGE IN BEHAVIOR
  ↓
INITIAL ACTORS / SCENARIOS
  ↓
KNOWN CONSTRAINTS
  ↓
INITIAL SCOPE
```

Initial Scope ещё не является окончательным impact scope.

Это только стартовая гипотеза, которую дальше нужно расширить через зависимости и ownership.

## Какие вопросы задавать

```text
Что должно стать возможным после изменения?
Что должно перестать происходить?
Для кого меняется поведение?
В каком сценарии?
Какая часть поведения должна остаться неизменной?
Есть ли обратная совместимость?
Есть ли временные или migration-ограничения?
Какие внешние системы явно участвуют?
```

## Не путать request и scope

```text
Request:
"Добавить retry покупки"

Initial Scope:
"Пользователь должен получить корректный access status,
если подтверждение покупки временно недоступно"
```

Во втором варианте уже видно, что изменение может затронуть не только retry-механику, но и:

- access state;
- billing reconciliation;
- degraded behavior;
- trust window;
- UI feedback;
- verification criteria.

## Метод

### 1. Отделить цель от предложенного решения

Сначала перепишите запрос без технического способа реализации.

### 2. Назвать наблюдаемое изменение

Что станет иначе для пользователя, соседней системы или оператора?

### 3. Зафиксировать неизменяемое

Что не должно поменяться даже после реализации?

Это важная часть scope: она задаёт будущие regression-инварианты.

### 4. Отметить явные boundaries

Какие responsibility zones и внешние системы уже очевидно участвуют?

### 5. Зафиксировать неизвестные

Initial Scope не должен притворяться полным.

```text
KNOWN
OPEN
ASSUMPTION
```

лучше, чем скрытые догадки.

## Результат

Хороший Initial Scope обычно содержит:

```text
Goal
Observed behavior change
Primary actors
Primary scenario
Known affected boundaries
Must-not-change invariants
Constraints
Open questions
```

## Пример Aveli

Запрос:

> Пользователь должен иметь возможность временно пользоваться приложением без сети после подтверждения подписки.

Плохой scope:

```text
Изменить локальную проверку подписки во Flutter.
```

Лучший Initial Scope:

```text
Goal:
сохранить доступ на ограниченное время при отсутствии сети.

Observed change:
клиент может разрешить доступ без онлайн-проверки backend.

Known boundaries:
frontend, backend access authority, billing evidence.

Must not change:
клиент не становится постоянным владельцем access decision.

Open:
какой trust window допустим?
как отзывается доступ?
что происходит после expiry?
```

Уже на этом этапе видно, что задача касается trust, access ownership и failure behavior, а не только Flutter-кода.

## Типичные ошибки

### 1. Scope = список компонентов

```text
backend + frontend + db
```

не объясняет, **что именно** меняется.

### 2. Scope = готовое решение

Так аналитик подтверждает предположение до анализа.

### 3. Нет must-not-change условий

Без них сложно проверять регрессии и совместимость.

### 4. Слишком ранняя полнота

Initial Scope обязан быть уточняемым.

## Проверка

Перед переходом к Change Surface должно быть понятно:

```text
[ ] зачем нужно изменение
[ ] какое наблюдаемое поведение меняется
[ ] кто это поведение наблюдает
[ ] какой основной сценарий затронут
[ ] что должно остаться неизменным
[ ] какие boundaries уже очевидны
[ ] какие вопросы ещё открыты
```
