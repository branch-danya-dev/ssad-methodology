# Storage Hierarchy

Физическая структура знаний должна помогать читателю ориентироваться в системе.

> **Хранение иерархично. Знание связано графом.**

## Проблема

Если структура строится только по типам артефактов:

```text
requirements/
diagrams/
api/
security/
```

то знание об одной responsibility zone оказывается разорвано между множеством каталогов.

Читатель вынужден сам собирать систему из фрагментов.

## Принцип

Физическая иерархия должна по возможности отражать устойчивые зоны ответственности реальной системы.

Например:

```text
business/
backend/
frontend/
database/
integrations/
system/
```

Это не обязательный шаблон SSAD. В другой системе естественная декомпозиция будет другой.

## Не копируй source tree механически

Системная структура и структура кода могут совпадать частично, но это не цель.

Плохой критерий:

> «Так устроены папки в репозитории кода, значит так же должна выглядеть документация».

Хороший критерий:

> «Эта область имеет самостоятельную ответственность, знания, решения и границы, поэтому она заслуживает собственного места».

## Ответственность каждого уровня

Каждый каталог должен отвечать на один крупный вопрос, а каждый документ — на один ограниченный вопрос.

Если нельзя в одном предложении объяснить, зачем существует директория, её ответственность размыта.

## Размер не равен сложности

Десять небольших файлов с ясным ownership могут быть проще одного файла на 1500 строк.

Цель — минимизировать не количество файлов, а стоимость поиска, чтения и изменения знания.

## Проверка структуры

Для каждого элемента дерева спросите:

```text
Почему эта область существует?
Какую ответственность она представляет?
Почему это знание находится здесь?
Можно ли найти его без знания всей структуры репозитория?
```
