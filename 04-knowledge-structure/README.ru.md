# 04 · Knowledge Structure

Этот раздел отвечает на вопрос:

> **Как превратить результаты анализа в базу знаний, где легко найти локальную истину, понять её владельца и проследить связи с остальной системой?**

SSAD не задаёт универсальное дерево директорий. Вместо этого структура выводится из реальной системы, её responsibility zones и ownership.

## Основной путь

```text
ANALYSIS RESULT
      ↓
CANONICAL OWNER
      ↓
STORAGE HIERARCHY
      ↓
KNOWLEDGE LINKS
      ↓
PROGRESSIVE DEPTH
      ↓
TEAM CONSUMPTION
```

Физическое хранение и логические связи решают разные задачи:

```text
Хранение — иерархично.
Знание — связано графом.
```

## Темы раздела

1. [`canonical-ownership/`](canonical-ownership/) — где живёт основной источник истины и почему один факт должен иметь одного канонического владельца;
2. [`storage-hierarchy/`](storage-hierarchy/) — как организовывать физическую структуру вокруг ответственности системы, не превращая её в механическую копию source tree;
3. [`knowledge-links/`](knowledge-links/) — как связывать локальное знание с зависимостями, flows, interfaces, decisions и change surface без дублирования истины;
4. [`progressive-depth/`](progressive-depth/) — как дать новичку overview, а специалисту — прямой путь к нужной глубине.

## Главный принцип

> **Не дублируй знание. При необходимости дублируй только контекст.**

Локальный документ может объяснить, почему чужое правило важно именно здесь, но его каноническое определение остаётся у владельца.

## System-shaped не означает source-shaped

Структура вида:

```text
business/
backend/
frontend/
database/
integrations/
system/
```

может быть хорошей, если эти области действительно отражают ответственность анализируемой системы.

Но это не шаблон SSAD. Для другой системы правильная декомпозиция будет другой.

Критерий — не сходство с кодом, а ясность responsibility и ownership.

## Хорошая база знаний должна отвечать

```text
Где находится канонический факт?
Почему он находится именно там?
Кто им владеет?
Какой локальный контекст нужен здесь?
С какими другими знаниями он связан?
Насколько глубоко нужно читать для текущего вопроса?
```

## Критерий качества

Репозиторий может содержать сотни файлов и всё равно быть простым, если пользователю не нужно понимать сотни файлов одновременно.

> Хорошая knowledge architecture делает большой репозиторий субъективно маленьким.
