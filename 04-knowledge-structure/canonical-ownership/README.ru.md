# Canonical Ownership

Каноническое владение отвечает на вопрос:

> **Где находится основной источник истины для конкретного знания?**

SSAD не требует, чтобы всё знание о системе находилось в одном документе. Но для каждого значимого факта должен существовать **один канонический владелец знания**.

## Проблема

Когда одно и то же правило независимо описано в нескольких местах, возникает расхождение:

```text
backend/access.md
→ trial = 7 дней

frontend/paywall.md
→ trial = 14 дней

requirements/subscription.md
→ trial = 7 дней
```

Читатель уже не знает, чему верить.

## Принцип

```text
ONE FACT
   ↓
ONE CANONICAL OWNER
   ↓
MANY CONTEXTUAL REFERENCES
```

Например, если решение о доступе принимает backend, то правило доступа канонически описывается в зоне backend/access. Frontend, billing flow и QA-сценарии могут повторять локальный контекст, но должны ссылаться на каноническое правило.

> **Не дублируй знание. При необходимости дублируй только контекст.**

## Как выбрать владельца знания

Задайте вопросы:

```text
Кто принимает решение?
Кто хранит авторитетное состояние?
Кто отвечает за корректность правила?
Где изменение этого знания должно происходить первым?
```

Физическое расположение должно следовать за логическим ownership, а не за тем, где правило впервые понадобилось автору документа.

## Контекстное повторение допустимо

Плохое дублирование:

```text
frontend/paywall.md
Trial lasts 7 days.
```

если эта фраза становится самостоятельной второй истиной.

Хороший контекст:

```text
Frontend shows the trial state returned by Access.
See canonical access policy: ../backend/access/trial.md
```

## Проверка

Для любого существенного утверждения должно быть возможно ответить:

- где его канонический источник;
- почему он находится именно там;
- кто обязан обновить его при изменении системы;
- какие другие документы только потребляют это знание.
