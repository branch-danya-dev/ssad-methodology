# Knowledge Contribution

SSAD рассматривает команду не как набор получателей документации, а как **распределённый источник системного знания**.

Главный вопрос:

> Какое знание конкретный участник команды способен подтвердить, опровергнуть или дополнить?

## Почему роли недостаточно

Фраза «поговорить с разработчиком» ничего не говорит о цели взаимодействия.

Полезнее определить, **какое утверждение требует проверки** и кто обладает подходящим evidence или authority.

Пример:

```text
Утверждение:
Backend может хранить refresh token.

Developer
→ подтверждает фактические ограничения реализации

Architect
→ подтверждает допустимость решения

Security
→ подтверждает требования к хранению секрета

Identity provider owner
→ подтверждает, выдаётся ли token вообще
```

## Типичные источники знания

| Участник | Что обычно способен подтвердить |
|---|---|
| Client / Requester | исходную проблему и ожидаемый эффект |
| Product / Business | бизнес-правила, приоритет, допустимое поведение |
| System Analyst | согласованную системную модель и связи |
| Architect | архитектурные ограничения и допустимые зависимости |
| Developer | факты реализации, техническую выполнимость, скрытые ограничения |
| QA | неоднозначности, edge cases, тестируемость |
| Integration Owner | внешний контракт, ограничения и фактическое поведение интеграции |
| Security | trust boundaries, требования защиты, недопустимые сценарии |
| Operations / Support | эксплуатационные факты, наблюдаемость, реальные failure modes |

Это не RACI и не фиксированная матрица ответственности. Один и тот же вопрос может требовать evidence от нескольких участников.

## Метод

Перед взаимодействием сформулируй:

```text
1. Какое утверждение я пытаюсь проверить?
2. Это вопрос факта, решения или ограничения?
3. Кто владеет этим знанием?
4. Кто может предоставить evidence?
5. Что будет считаться достаточным подтверждением?
```

## Evidence не всегда означает authority

Участник может знать, **как система работает сейчас**, но не иметь права определять, **как она должна работать**.

```text
Developer
→ implementation evidence

Product
→ business authority

Architect
→ architecture authority
```

SSAD хранит это различие явно.

## Результат

Хорошая коммуникация заканчивается не сообщением «обсудили», а изменением состояния знания:

```text
UNKNOWN
→ HYPOTHESIS
→ CONFIRMED / REJECTED / CONFLICTED
```

Если полученный факт влияет на каноническую модель, он должен попасть к её владельцу.

## Проверка

Перед завершением взаимодействия спроси:

- какое конкретно знание изменилось;
- кто это подтвердил;
- есть ли evidence;
- не противоречит ли оно другим владельцам знания;
- нужно ли обновить analysis/specification.

> **В SSAD команда участвует не потому, что её нужно "проинформировать", а потому, что системное знание распределено между участниками.**
