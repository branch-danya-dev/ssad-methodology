# Decision Resolution

В реальной работе участники часто дают несовместимые ответы.

```text
Product
→ пользователь должен сохранять доступ офлайн

Security
→ после отзыва доступа клиент не должен доверять локальному состоянию бесконечно

Developer
→ мгновенная online-проверка невозможна без сети
```

Это не «плохая коммуникация». Это нормальная ситуация, в которой нужно превратить конфликт требований, ограничений и evidence в **явное системное решение**.

## Сначала классифицируй конфликт

```text
FACT CONFLICT
→ источники по-разному описывают существующую систему

REQUIREMENT CONFLICT
→ stakeholders ожидают несовместимое поведение

CONSTRAINT CONFLICT
→ желаемое поведение сталкивается с техническим / security / legal ограничением

OWNERSHIP CONFLICT
→ несколько областей считают себя authority одного решения
```

## Не решай конфликт голосованием

Количество участников не определяет истинность.

Нужно понять:

- кто является authority по конкретному решению;
- какие ограничения обязательны;
- какие данные являются evidence;
- какие компромиссы доступны;
- какие последствия создаёт каждый вариант.

## Метод

```text
1. Запиши конфликтующие утверждения отдельно.
2. Укажи source / evidence / authority каждого утверждения.
3. Выдели обязательные ограничения.
4. Сформируй варианты решения.
5. Для каждого варианта опиши последствия и риски.
6. Получи решение от правильного decision owner.
7. Обнови каноническое знание.
8. Удали или перепривяжи устаревшие локальные формулировки.
```

## Пример: bounded offline trust

Конфликт:

```text
Product
→ офлайн-доступ нужен

Security
→ отозванный доступ не должен жить бесконечно

Technical reality
→ без сети невозможно немедленно узнать об отзыве
```

Решение может быть:

```text
Backend grants access
        ↓
Client stores signed/validated access evidence
        ↓
Offline use allowed within bounded validity window
        ↓
After expiry → online reconciliation required
```

Здесь компромисс не «среднее мнение». Это новая системная модель, которая сохраняет нужные свойства обеих сторон в пределах технической реальности.

## Decision record ≠ canonical knowledge

История решения полезна для вопроса:

> Почему мы выбрали этот вариант?

Но текущее поведение системы должно жить у канонического владельца знания.

```text
Decision record
→ rationale / alternatives / trade-offs

Canonical model
→ current truth
```

Нельзя заставлять читателя изучать старые решения, чтобы понять текущее состояние системы.

## Завершение конфликта

Конфликт закрыт только если:

- decision owner определён;
- решение принято;
- последствия понятны;
- каноническая модель обновлена;
- зависимые знания синхронизированы;
- старое утверждение больше не выглядит актуальной истиной.

> **Разногласие становится полезным, когда оно превращается в явное решение и улучшает модель системы.**
