# Кейс 001 — Aveli

[Английская версия](README.md)

## Тип кейса

```text
локальное мобильное приложение
клиент Flutter
серверная часть NestJS
локальное рабочее пространство SQLite
серверные данные учётной записи и доступа в PostgreSQL
платёжная интеграция RevenueCat
```

Полный проект: https://github.com/branch-danya-dev/aveli-system-analysis

## Почему Aveli оказалась полезным кейсом

В Aveli есть границы, которые легко смоделировать неправильно:

- локальные профессиональные данные и серверные данные учётной записи и доступа;
- ответственность клиентского приложения и авторитетность серверной части;
- внутренний интерфейс клиент↔сервер и внешние платёжные провайдеры;
- автономная работа и авторитетная серверная проверка доступа;
- механизм хранения и технология доступа к данным во время выполнения;
- компонентные знания и целостное системное представление.

## История построения

```text
подтверждения существующего проекта
→ бизнес-основа
→ разделение владения данными
→ ответственность клиента и сервера
→ границы интеграций
→ исправление владения технологиями
→ системный синтез
→ миграция устаревшей документации
→ проверка всей системы
→ Stable
```

## Что было проверено

- документация, отражающая устройство системы;
- каноническое владение знаниями;
- построение по зависимостям;
- владение данными до физического хранения;
- владение технологиями;
- разделение внутренних и внешних границ;
- анализ на основе подтверждений;
- двуязычная документация;
- системный синтез;
- трассируемость;
- проверка отказов и готовности к выпуску;
- переработка старой документации;
- итоговая проверка качества.

Кейс также привёл к изменениям самой методологии.
